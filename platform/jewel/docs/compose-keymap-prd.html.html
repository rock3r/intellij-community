Jewel Compose shortcuts and IntelliJ keymap

Product requirements and API proposal for a single Jewel shortcut API that works in standalone desktop apps and as an IntelliJ Platform (IJPL) bridge, without changing Compose or the IJPL action/keymap subsystem.

Status: proposed · Scope: platform/jewel and its IJPL bridge · Related: IJPL-212347

Decision

Use a two-lane model. Explicit Jewel commands are resolved through the host keymap (IJPL keymap in the bridge; a standalone keymap in standalone apps). Raw Compose key handlers may selectively claim a keystroke before IJPL lookup. A command is therefore configurable and visible to the host; a raw key claim is deliberately local and authoritative.

This is preferable to making all Compose input win (which breaks IDE shortcuts) or all IJPL actions win (the current bug). It also avoids duplicating or modifying IdeKeyEventDispatcher, KeymapManager, and Compose Desktop.

Evidence and constraints

  • IJPL resolves local and active-keymap actions, evaluates AnAction.update(), and may consume the event before the AWT focus target receives useful input. See platform/platform-impl/.../IdeKeyEventDispatcher.kt.
  • The dispatcher already has an early, purpose-built escape hatch: a focused KeyboardAwareFocusOwner can return true from skipKeyEventDispatcher(KeyEvent). This prevents IJPL action lookup while ordinary AWT dispatch continues.
  • Jewel already separates host-neutral UI/data contracts from IJPL-specific adapters and standalone defaults. It has no shortcut claim, focused-binding, or standalone keymap subsystem today; those are new work proposed here.
  • The current bridge contributes Compose data to IJPL through UiDataProvider and bridges paste semantics, but it does not participate in pre-keymap key ownership. Its menu shortcut provider is display-only.

Important qualification: the actual AWT focus owner is the nested ComposePanel, not JewelComposePanelWrapper. The bridge must use a focus-owner implementation or proxy that implements KeyboardAwareFocusOwner; merely adding that interface to the wrapper will not work.

Conceptual model and precedence

AWT KeyEvent
  │
  ├─ focused Jewel host: does a focused UI subtree explicitly claim this raw key?
  │    ├─ yes → skip IJPL keymap; deliver to Compose; run local handler
  │    └─ no
  │
  ├─ host command resolver
  │    ├─ IJPL: active Keymap → registered/standard AnAction → Compose-aware DataContext
  │    └─ standalone: configured/default keymap → Jewel command handler
  │
  └─ ordinary Compose key delivery and component navigation
  1. Explicit raw claim wins. It is the escape hatch for a focused editor-like component, a modal Compose interaction, or an intentional conflict.
  2. Host command keymap wins next. This preserves user keymap customisation and familiar IJPL behaviour for commands such as Copy, Paste, Find, and tool-window actions.
  3. Unclaimed Compose input remains normal Compose input. An unbound key is never swallowed by the new API.

Public API proposal

Place this API in a new host-neutral org.jetbrains.jewel.foundation.shortcut package (or a focused foundation submodule). It uses Compose key types only and has no com.intellij.* imports.

shortcut(action) is an action binding: it supplies availability and invocation for one host-registered JewelAction, while the host resolver owns keymap bindings. JewelActionDefinition is the complete host-neutral catalog item: title/semantics plus default keyboard bindings. In IJPL, register() first attaches to a same-ID JewelActionBridgeAction declared by plugin.xml, validating compatible template metadata without re-registering the AnAction; otherwise it registers a runtime bridge action. In standalone it declares the catalog item. Every host must resolve an ID or report a configuration error; no action is silently unavailable in standalone.

claimShortcut claims a physical KeySequence, including a two-stroke chord, before host keymap lookup. claimKeyEvent is the deliberately low-level single-event escape hatch for editor-like input that is not a shortcut sequence. A matching enabled raw-event claim irrevocably owns and consumes the event, then invokes onKeyEvent; it never falls through to the host keymap or later ordinary Compose handlers. They are separate rather than implicit onPreviewKeyEvent behavior so bypassing user keymap customisation is visible in source review. A sealed ShortcutBinding overload could combine the names later, but action bindings, sequence claims, and raw-event claims must remain distinct.

Claimed sequence state

A sequence claim uses one/two-stroke state that is explicit and identical in both hosts. An exact one-stroke claim wins immediately over a longer claim sharing its first stroke; the longer sequence is therefore not entered. For a prefix with no exact candidate, the focused claim resolver selects candidates in inner-to-outer modifier order, consumes the first stroke, and enters pending state. In IJPL it also makes the focused host skip IdeKeyEventDispatcher for that prefix; in standalone the window-root pre-key resolver consumes it before ordinary Compose handlers.

  • The pending state holds the focused host and candidate snapshot. Focus transfer, disposal, or timeout cancels it.
  • A matching second stroke invokes the innermost enabled exact claim and consumes the stroke. Multiple claims sharing a prefix are therefore supported.
  • A nonmatching second stroke cancels pending state and is consumed; the already-consumed prefix is never replayed. This deliberately matches IJPL’s conservative chord behavior rather than leaking an unexpected second input to a text field.
  • blocksOuterClaims prevents outer modifier/ancestor claims from participating for the same prefix, including after an inner claim becomes disabled.

Repeat delivery

ShortcutRepeatPolicy is a Jewel resolver policy, not a claim about platform auto-repeat behavior. On every delivered auto-repeat key-down for a completed one-stroke Jewel binding, the resolver re-evaluates availability and may invoke it again. OnceUntilRelease suppresses later delivered key-down repeats until the final key-up and is appropriate for non-repeatable operations such as opening a dialog or toggling an exclusive mode. Existing mapped IJPL actions retain IJPL’s native repeat behavior.

  • Repeat state is tracked per focused host and physical key sequence; key-up clears the one-shot latch.
  • A two-stroke prefix never repeats: repeated first-stroke key-downs are consumed while pending, and only the completed sequence may invoke repeatedly.
  • Focus transfer, modifier release, timeout, or disposal clears repeat and pending-sequence state.
  • The IJPL bridge applies the policy only for bridge-owned Jewel bindings; standalone applies it in its window-root resolver. Pointer and programmatic invocation are unaffected.

Focus-path selection and overrides

A command ID does not identify one global callback. It identifies a host-visible action whose target is selected from the focused Jewel UI tree at invocation time. Each shortcut call is a binding modifier node, not action registration. The bridge/standalone resolver maintains the currently focused node and walks its Jewel ancestor path from leaf to root.

// Outer container supplies the ambient fallback.
Box(Modifier.shortcut(SelectAllRows) { table.selectAll() }) {

  // A focused embedded editor overrides precisely that same action.
  Editor(
    Modifier.shortcut(SelectAllRows) { editor.selectAllText() }
  )
}
  1. Resolve only registrations on the focused node and its Jewel ancestors.
  2. Choose the nearest enabled registration for the command ID; an unavailable registration falls through to its parent.
  3. A registration can declare blocksOuterBindings = true to intentionally disable outer/ambient handlers rather than fall through.
  4. When focus leaves the Jewel host, no Jewel registration participates.

Modifier-chain semantics

  • Different actions never clash. Multiple shortcut modifiers on one UI node, such as Cut, Copy, and Paste, are independent entries keyed by JewelActionId.
  • Duplicate action on one node follows normal modifier order. The resolver walks modifier entries inner-to-outer (rightmost applied modifier first), matching Compose onKeyEvent bubbling. Thus Modifier.shortcut(copy, outer).shortcut(copy, inner) selects inner while it is enabled.
  • The selected entry owns its blocking policy. For duplicate bindings, the rightmost entry’s blocksOuterBindings value wins; flags are never merged. If that entry is disabled and does not block, traversal reaches the next outer entry, whose own flag then governs subsequent fall-through.
  • Disabled bindings fall through. If the inner duplicate is disabled, lookup continues to the outer duplicate and then the parent UI node. If the entry currently being evaluated has blocksOuterBindings = true, lookup stops and the action is unavailable.
  • Raw claims use resolver selection. For multiple matching claimKeyEvent records, the resolver selects the innermost enabled record by published modifier order, consumes before ordinary Compose dispatch, and invokes only that handler. Sequence claims use the same inner-to-outer modifier order when selecting their first-stroke candidate; the selected/rightmost candidate’s blocksOuterClaims flag governs traversal, without merging flags from duplicates.

No public ShortcutScope is needed. Each shortcut modifier publishes an immutable binding record into a host-owned registry: its focus-anchor token, parent token, modifier order, and current atomic binding snapshot. Focus modifiers publish the currently focused anchor token. The resolver follows those recorded parent links and orders records by the published modifier order; it does not attempt to traverse arbitrary Compose modifier/layout internals, use composition order, or use a global “last registered wins” list. Delegated modifiers and interop must explicitly choose the nearest focus anchor when attaching.

Action taxonomy: semantics, not an AnAction hierarchy

Jewel should not reproduce IJPL inheritance classes. IJPL base classes combine platform execution, Swing rendering, dumb-mode capability, and menu construction; Jewel keeps only cross-host semantics in its action descriptor and composes UI separately.

  • Lazy and context-sensitive children: groups expand against the same focused host ActionContext used by leaf actions. Their child list is sampled by the shared scheduler only while a menu/toolbar consumes it. Version one treats group presentation as static descriptor metadata; context-dependent group text/icon/visibility is deferred until an explicit group update contract exists.

Toolbar and popup-group expansion

  • ActionToolbar: expands visible non-popup groups recursively, renders leaf actions as action-bound toolbar controls, and renders a visible popup = true group as an ActionMenuButton. Secondary entries are retained as overflow candidates rather than discarded.
  • ActionMenu: renders groups as submenus, separators as separators, and leaves through ActionInvoker. It resolves the group against the focused ActionContext immediately before opening, so dynamic child actions are current.
  • Action that opens a menu: model it as a popup JewelActionGroup and render ActionMenuButton(group). This is the Jewel equivalent of an IJPL popup ActionGroup/ComboBoxAction; it is not a fake leaf JewelAction.
  • Action plus menu: model it as SplitActionButton(primary, menu). The primary half invokes a real leaf action; the disclosure half opens a group. This mirrors IJPL split-button behavior without introducing a split-action subclass.

Standalone and composition lifetimes

Standalone global registration is explicit: the application owns an ActionRegistration handle and closes it when its application, feature, or plugin-equivalent lifetime ends. A standalone application may create an action catalog at startup, retain all handles in its application object, and pass the registry into IntUiTheme. No Compose tree needs to remain alive for these globally discoverable actions to stay in the keymap.

@Composable
fun RegisterAction(action: JewelAction) {
    val registry = LocalJewelActionRegistry.current
    DisposableEffect(registry, action) {
        val registration = registry.register(JewelActionDefinition(action))
        onDispose { registration.close() }
    }
}

RegisterAction is the easy composition-scoped API for ephemeral feature actions. The registry reference-counts identical registrations by action ID and rejects incompatible duplicate descriptors. It must not be used for an action that should remain visible in settings/keymaps after the composable disappears. ActionRegistration.close() is idempotent, so manually closing a registration that was also closeWith-attached is safe; parent disposal merely performs a harmless second close. The bridge adapter is generic and belongs solely to the bridge artifact, so the common registry stays free of IJPL lifetime types and standalone callers never encounter a bridge-only overload.

JewelActionBridgeAction is a generic bridge action: during update() and actionPerformed() it obtains its own registered action ID from ActionManager, then resolves that ID against the focused Jewel path. It holds no Compose state. This makes declarative and runtime actions identical from the keymap’s perspective.

collectPresentationAsState() reads the host registry from an internal CompositionLocal; application composables do not configure or own polling. The bridge provides the application-level registry at JewelComposePanel creation and IntUiTheme provides the standalone registry. Each collection registers a stable reference-counted demand key of (collector ID, action ID, host/window context); the current focus stamp is generation metadata on its sample. Identical update requests share one sample and one global scheduler tick. DisposableEffect removes the demand when the collector leaves composition. No composable creates a poll loop.

This is an additive API: callback-based ActionButton(onClick = …), IconActionButton, and toggle controls stay intact. The action overload collects only the presentation projection it renders, uses enabled for interaction, omits the composable when visible is false and respectVisibility is true, uses selected for toggle/selected controls, and supplies text, description, and icon to the component’s normal styling and accessibility paths.

ToggleActionButton(action), ToggleMenuItem(action), and radio-style menu components require action.kind == Toggle; they render the same dynamic selected state with their respective accessibility role. A toggle’s handler updates its external state, and the next action presentation sample reflects the new selection—there is no common setSelected method to mirror.

Enabled and visible are independent

The model preserves IJPL Presentation semantics instead of exposing a single “available” flag.

StateMeaningEffect
enabledWhether the action may execute in the current focused context.Controls keyboard/manual execution and disabled styling. A disabled action is never invoked.
visibleWhether the action should be rendered in menus, toolbars, and action-bound controls that respect visibility.Controls presentation only. A hidden but enabled action remains eligible for a keymap shortcut or explicit programmatic invocation, matching IJPL behavior.

Modifier.shortcut(enabled = …, presentation = ActionPresentationOverride(visible = PresentationValue.Set(…))) updates them independently. If no focused binding is found, the bridge sets enabled = false but preserves template visibility; this lets a declared action remain discoverable in non-compact menus while correctly refusing execution. Standalone applies the same rule to its action catalog presentation.

Action lifecycle events

ActionEventSource.invocations is the host-neutral observation point for cross-cutting features such as a Presentation Assistant, structured action logging, analytics, and black-box UI tests. “Executed” has one deliberately narrow meaning: a resolved Jewel callback returned normally. It is not a business-operation completion signal. Each bridge-owned/standalone dispatched request carries a registry correlation token, and the source emits at most one matching boundary event with the final presentation and trigger.

@Composable
fun PresentationAssistant(events: ActionEventSource) {
    val invocation by events.invocations.collectAsState<ActionInvocation?>(initial = null)
    invocation?.let { showPopup(it.presentation.text, it.trigger) }
}

The action registry is the single publisher boundary for BridgeOwned actions: keyboard resolution, ActionButton clicks, and programmatic execution must all flow through it and produce at most one event. A MappedIdeAction preserves IJPL ownership: neither keyboard nor invoker execution emits a Jewel lifecycle event, because tryToExecute cannot safely carry a Jewel correlation through arbitrary asynchronous platform dispatch. Consumers observe those actions through ordinary IJPL facilities.

Manual invocation

Use rememberActionInvoker() from any Compose code, including a custom action-bound component. It requests the action from the host rather than calling a bound callback directly, so it preserves update/enablement checks, lifecycle boundaries, and IJPL action callbacks. Repeat policy applies only to keyboard dispatch.

@Composable
fun ExportLink(action: JewelAction) {
    val invoker = rememberActionInvoker()
    Link("Export", onClick = { invoker.invoke(action, ActionTrigger.Pointer) })
}

In IJPL, the invoker resolves either a BridgeOwned action (which requires a focused Jewel binding) or a MappedIdeAction (which uses the platform action’s own DataContext behavior), then calls ActionManager.tryToExecute with the data-provider host component and action place. In standalone, it resolves a focused binding through the action registry. Request submission alone does not imply that a disabled or stale action executed; mapped actions report only dispatch acceptance, not a Jewel completion event.

Failure, lifecycle, and race contract

Misconfiguration and lifecycle races must be visible and safe; no route is allowed to silently invoke an arbitrary fallback callback.

  • Duplicate IDs: exact duplicate action descriptors may be reference-counted; differing descriptors for the same ID fail registration with a diagnostic. IJPL plugin.xml collisions retain the platform’s registration error behavior.
  • Stale keymap entries: keymaps may retain mappings for an action that was removed. Both hosts leave those keystrokes unconsumed, report one coalesced stale-mapping diagnostic, and preserve the mapping for future re-registration or settings cleanup.
  • Disposed host: collectors return disabled HostUnavailable fallback state, dispatch returns Rejected(HostUnavailable), and scheduler demand/pending sequences are cancelled.
  • Programmer feedback: development builds may surface a visible diagnostic/inspection for unregistered action use; production behavior remains disabled and non-throwing inside composition.

Dynamic enablement and presentation

JewelAction is an immutable identity and default presentation. A focused Modifier.shortcut owns the dynamic state for that UI location: the independent enabled execution gate plus ActionPresentationOverride fields, including visible. PresentationValue.Inherit leaves a template value intact; Set(null) deliberately clears nullable fields such as an icon. Modifier updates publish an atomically replaceable immutable binding snapshot (including callback/version) on Compose-safe updates; IJPL and schedulers read only that snapshot and take an execution lease that is rechecked immediately before invocation. The bridge merges the focused binding’s override over the action/template presentation, while standalone performs the same merge over its action catalog default.

    enabled = canExport,

Action-bound composables do not call update() during recomposition. JewelAction.collectPresentationAsState() registers demand with one host-level presentation scheduler while it is collected. A poll first normalizes the real host presentation and compares it with the last published presentation; the scheduler writes its State<ActionPresentation> only when they differ by equality. An unchanged poll therefore triggers no invalidation or recomposition.

Controls then observe only what they render through the selector overload of collectPresentationAsState. For example, an icon-only action button selects ActionIconButtonState(icon, enabled, visible, selected); a change to text or description alone does not recompose that button. A text button includes text, while a tooltip includes description. The derived selected value is likewise equality-gated, so a control recomposes only when the part of real action state it displays is dirty.

  1. Poll, then recompose: IJPL uses one bridge presentation scheduler per application, registered with the platform action-update timer/cadence. Demand is keyed by stable (collector ID, action ID, host context); a focus stamp is sample-generation metadata, not part of the key. On focus change, demand migrates atomically to the newest generation and deduplicates update requests. One action shared by several visible Jewel controls in the same context is updated once per tick. It never starts an update from a composition or modifier callback.
  2. Focus/traversal: focus changes, node attach/detach, and modifier-chain changes publish a new immutable focused-path snapshot and advance a focus stamp. They invalidate the affected stable demands; the next poll reads the latest snapshot. JewelActionBridgeAction.update() reads this snapshot on EDT and never invokes composition.
  3. External non-Compose state: callers that cannot expose Compose-observed state call ActionRegistry.invalidate(actionId?). This only marks matching sampled entries dirty (and may request a coalesced normal UI refresh); it does not synchronously run or fan out update() calls. The next poll rereads a thread-safe external snapshot.
  4. Stale safety: actionPerformed() and ActionInvoker.invoke() always resolve current state again, so an action disabled after its last visual update cannot execute.

Standalone uses the same demand/deduplication/stale model with its window action scheduler. Its cadence is configurable by the host, and it polls only actions with an active presentation consumer (visible action composables, open menus, or shortcut-feedback UI). This prevents a large hidden Compose tree or a spammy action from creating per-recomposition update traffic.

Bridge implementation

  1. Resolve: action.collectPresentationAsState() resolves the action ID through the host registry. The IJPL adapter may map a standard Jewel action to an existing IDE action; a standalone adapter resolves the same Jewel action through its own registry. Missing mappings are reported consistently as host configuration errors.
  2. Update: the bridge presentation scheduler invokes the action’s standard IJPL update path against the current Jewel host DataContext, respecting ActionUpdateThread and the platform’s polling cadence. It copies the resulting IJPL Presentation into immutable ActionPresentation state. Updates are deduplicated and demand-driven—not performed by composition, focus callbacks, or individual invalidations.
  3. Perform: the control obtains rememberActionInvoker() and calls invoke(action, Pointer); the bridge calls ActionManager.tryToExecute(action, null, hostComponent, place, true). It does not call actionPerformed() directly. Thus listeners, transactions, dumb-mode handling, and the focus-path command resolver all remain on the IJPL path.
  4. Icons: the bridge adapts an IJPL Icon to Jewel IconKey (or a bridge painter) at the boundary. The common model exposes no Swing type.
  5. Lifecycle: the bridge-owned registry emits one correlated ActionInvocation after its resolved callback returns normally. Mapped IDE actions stay in IJPL’s lifecycle facilities. The standalone resolver emits the same event after its handler returns successfully.

For a Jewel action, its registered bridge AnAction.update() resolves the focused leaf-to-root handler described above. Therefore an ActionButton and the same action’s keyboard shortcut always agree on visible, enabled, selected, and execution behavior.

Standalone keymap and dispatch

Standalone is not “a list of hard-coded onKeyEvent checks.” It is a keyboard-only analogue of the IJPL keymap subsystem: named schemes, parent inheritance, effective action-to-shortcut mappings, conflicts, two-stroke sequences, an active-keymap manager, and runtime mutation. Mouse shortcuts are the sole intentionally omitted capability in the first version. The same action registry and modifier bindings are used in both hosts.

KeyStroke here is a host-neutral Jewel value type based on Compose Key and modifier flags—not javax.swing.KeyStroke. KeySequence deliberately has one or two strokes, matching IJPL KeyboardShortcut. JewelActionDefinition contributes default bindings; IntUiTheme supplies OS-specific defaults for built-in actions. The application may layer persisted user schemes above those defaults without changing its composables. The standalone configuration owns timeout and conflict ordering: candidates sort by descending priority, then ascending stable action-ID string, so equal priorities are deterministic. The IJPL bridge follows the platform timeout and action promotion rules.

Standalone event order

  1. The standalone host installs one window-root onPreviewKeyEvent resolver. It first consults only published claimShortcut/claimKeyEvent records from the focused path; arbitrary application preview/key handlers are not claims.
  2. If no claim matches, it queries the active JewelKeymap and the focused binding snapshot before ordinary Compose handlers receive the event.
  3. It orders enabled candidates using the action registry’s explicit priority (the standalone counterpart to IJPL action promotion) and invokes the nearest matching binding for the selected action ID.
  4. Only an explicit claim, an enabled exact command, or a valid chord prefix is consumed. Otherwise it returns false, allowing normal Compose preview/key handlers and component navigation to proceed.

This gives standalone the same semantic precedence as the bridge: focused raw input first, host keymap actions second, ordinary unbound input last. Unlike IJPL, it is a root Compose preview handler; the ordering is intentionally installed before arbitrary descendant handlers to preserve the explicit-claim policy.

Sequences, conflicts, and updates

  • Two-stroke shortcuts: an exact one-stroke action wins immediately over a longer sequence with the same first stroke. Otherwise focused sequence claims and mapped keymap actions use pending-sequence state. A matching first stroke is consumed, waits for the second with the configured timeout, and cancels on focus change. A nonmatching second stroke clears the state and is consumed.
  • Conflicts: a keymap may contain several action IDs for one sequence. The resolver filters to focused, enabled bindings, then applies explicit action priority. Default keymaps must not ship unresolved ambiguities; user schemes may retain conflicts with diagnostics.
  • Live rebinding: updates to a mutable scheme or active-keymap switches publish changes. Menu hints and collected action presentations refresh through the shared registry; no recomposition of modifier bindings is required.
  • Persistence: Jewel provides the in-memory scheme, inheritance, and import/export model. Whether overrides are serialized, synchronized, or surfaced in settings remains an application decision.

IJPL registration detail

The bridge owns one registry per application and a focused-path tracker per Compose host. Startup plugin.xml actions stay registered for the plugin/application lifetime; their matching JewelActionDefinition is attached during startup rather than re-registered. Runtime registrations create and own a bridge AnAction only when the ID is not already declaratively owned. A modifier binding never controls registration lifetime.

Route configuration is explicit. The bridge exposes JewelActionMappings.map(jewelActionId, ideActionId) in its bridge artifact for standard-action adaptation. This creates a MappedIdeAction route and validates that the target exists; standalone never needs this mapping because it registers the same JewelActionDefinition as BridgeOwned. The common action API does not expose AnAction, nor does a common action become a no-op outside IJPL.

JewelActionBridgeAction contract

JewelActionBridgeAction is a public, no-argument bridge AnAction intended for normal plugin.xml action registration. Its IJPL action ID must equal the corresponding JewelActionId.value. It contains no Compose, project, component, or mutable presentation fields; all ephemeral state lives in the host’s focused-path snapshot and registry.

class JewelActionBridgeAction : AnAction() {
    override fun getActionUpdateThread() = ActionUpdateThread.EDT

    override fun update(event: AnActionEvent) {
        registryFor(event).update(actionIdFor(this), event)
    }

    override fun actionPerformed(event: AnActionEvent) {
        registryFor(event).perform(actionIdFor(this), event)
    }
}
  1. Locate: registryFor(event) obtains the focused data-provider Jewel host from the normal IJPL DataContext, then its immutable focused modifier-path snapshot. The focused AWT component and the data-provider host must resolve to that same tracker. No captured Compose lambda crosses action lifetime boundaries.
  2. Update: update() selects the nearest eligible snapshot for its ID. It copies enabled state and merges the binding’s ActionPresentationOverride over template text, description, icon, visibility, and selected state from plugin.xml. EDT is required because selection consults UI/focus state and must be fast.
  3. Perform: actionPerformed() repeats resolution, obtains an execution lease, and invokes the selected callback only if the snapshot remains current and enabled. The surrounding IJPL action system provides callbacks, transactions, and dumb-mode checks.
  4. Lifecycle: after the callback returns normally, the registry emits one correlated ActionInvocation. A disabled, missing, stale, or repeat-suppressed binding emits nothing.
  5. Dumb mode: provide a separate DumbAwareJewelActionBridgeAction class for declarative actions available during indexing. Version one runtime registration always creates the ordinary, non-dumb-aware bridge action; indexing-capable runtime actions must be declared up front until a reviewed host-neutral capability contract is added.

Existing IDE actions mapped to a standard Jewel action (for example Copy) retain their original AnAction class and use the explicit MappedIdeAction route. They do not require a focused Jewel callback: their native update(), presentation, and DataContext remain authoritative. They do not emit through ActionEventSource, including when launched through ActionInvoker; all such execution remains observable through ordinary IJPL lifecycle facilities.

Thus an IJPL keystroke for a bridge-registered Jewel action follows the normal path: KeymapManager → ActionManager → JewelActionBridgeAction.update() → JewelActionBridgeAction.actionPerformed(). The only exceptions are claimShortcut and claimKeyEvent: they deliberately declare local physical input ownership, bypassing the keymap before any action is selected. This lets Settings | Keymap bind a stable action ID and requires no extension to ActionManager, KeymapManager, or IdeKeyEventDispatcher.

Bridge surface and compatibility

  • Add one bridge entry point or overload: JewelComposePanel(..., shortcutHandling = JewelShortcutHandling.Enabled). Default Enabled makes the bridge work without changes at call sites.
  • Keep compose(), JewelComposePanel(), provideData, current menu APIs, and component onPreviewKeyEvent source-compatible.
  • Do not expose IJPL KeyStroke, AnAction, DataKey, or IDE action IDs from common Jewel types. The bridge maps a host-neutral JewelActionId to an existing IJPL action where appropriate; standalone maps the same ID to its own resolver.
  • Do not replace existing platform Copy/Cut/Paste/Select All actions. Complete their Compose semantic/data-provider adapters in the bridge so the existing action IDs remain the primary integration point.

Implementation slices

  1. Feasibility spike: prove a Jewel-owned actual focus component can implement/proxy KeyboardAwareFocusOwner, that its data-provider component resolves to the same host tracker, and that an active IJPL second-stroke state cannot become orphaned when a Jewel claim begins. If this cannot be proven without changing IJPL/Compose, do not ship raw claims; NonLockedEventDispatcher is not an equivalent fallback.
  2. Foundation API: add action, modifier binding, claim, and resolver contracts; add host-neutral unit tests.
  3. Standalone resolver: adapt present default shortcut providers and sample wiring.
  4. IJPL resolver: focused-subtree tracker, lifecycle-safe dynamic actions, semantic edit providers, keymap menu hints.
  5. Conflict suite: execute the proof matrix on all supported desktop OSes and update Jewel API compatibility dumps for public additions.

Open decisions for implementation review

  • Whether custom Jewel actions are registered eagerly at application start (best Keymap settings discoverability) or while a runtime feature owner exists (smallest registry footprint). Recommendation: eager registration for documented application actions; runtime-bound registration only for ephemeral/internal actions.
  • Whether a standalone persistent keymap belongs in Jewel or remains an app-provided resolver. Recommendation: Jewel provides a default in-memory resolver and extension point; persistence remains application policy.
  • Whether standard action mappings (for example JewelActions.Copy → IdeActions.ACTION_COPY) are supplied entirely by the bridge or may be overridden by an application. Recommendation: bridge defaults plus an explicit, validated host override hook.
